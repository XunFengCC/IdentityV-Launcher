# 版本命名约定

2026-09-09，风吟为第一版选择 **1.0.0-rc.1** 作为首个发布候选的版本名。该候选已于 2026-09-23 公开发布（Git tag `v1.0.0-rc.1`，提交 `3bac291`）。此前“Alpha 1 / Alpha1-RC1”为开发候选名称，后续不再用于新包。已发布物、后续开发和本机安装物必须分开识别；实际行为与待修复问题见[变更记录](../CHANGELOG.md)和[已知问题](../docs/knownIssues.md)。

2026-09-10 补充封版节奏：RC1 已打通基本可用性，目前尚无首位外部用户，RC2 不急于封版。日常修复持续提交、验证和积累，不按一个补丁对应一个 RC，也不因为本机装了新修复就自动改发行号或封包。由风吟判断何时有阶段性进步，再确定下一次 RC 的范围与封包；emoji 修复当前记为 RC1 之后的未封版改进，不预先锁定为 RC2。

采用[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)的格式和预发布顺序，并将应用的用户可见行为、安装/配置格式与集成接口作为兼容性判断依据：

| 版本 | 项目含义 |
| --- | --- |
| `1.0.0-rc.1` | 2026-09-23 已公开的首个发布候选；字节与 Git tag 固定 |
| `1.0.0-rc.2` | 下一次公开封包可用的候选号；范围和发布时间尚未确定 |
| `1.0.0` | 第一版正式发布 |
| `1.0.1` | 向后兼容的问题修复 |
| `1.1.0` | 向后兼容的新功能 |
| `2.0.0` | 重大不兼容变化 |

`0.x`表示早期、尚未承诺稳定的阶段，本身不等于测试版；`rc`表示目标版本的发布候选。两者可以同时使用，但不符合本项目目前准备发布第一版的意图。若未来用alpha/beta，则顺序为alpha→beta→rc→正式；不需要为了形式补发未经历的阶段。

公开发布后，同一版本号对应固定发行物；后续修改可以先留在开发提交中积累，再次公开封包时使用新版本号。内部构建可递增构建号，但不能以只改构建号的方式覆盖已公开发布的同名发行物。正式签名/公证也应在候选公开发布前完成；公开的新候选相对旧候选有二进制变化时，递增 rc。此处约束发行物不可覆盖，不要求每次修改立即发行。

`playerLauncherApp/Info.plist`是版本数据源：`CFBundleShortVersionString`保留macOS要求的纯数字基础版本，`IdentityVReleaseVersion`记录完整版本，`CFBundleVersion`为内部构建号。关于窗口、版本与更新提示和DMG/材料包名读取这份数据。实际第三方组件（例如 idv-login 6.3.0、Wine）的独立版本不随启动器一起改号；发行材料中的组件版本和源码引用仍须与这份 App 实际携带的下载清单/补丁版本相符。

候选定稿、正式签名公证和公开发布是分别记录的动作。RC1 已公开，后续源码或运行时变化不得再沿用这个发行号。构建脚本把源码提交、发行号、运行时版本与默认 engine、包内清单哈希写进 `build-provenance.json`；封包前核对它们，并拒绝已存在 Git tag 的发行号。这能挡住“编译的是另一套运行时”及同号重封，但不能替代游戏内功能实测。若只是日常开发构建，仍可沿用当前版本号，直到决定下一次封包范围。
